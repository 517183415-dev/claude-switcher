## 5. 报告返回后的版本与 worktree 方案

**采用一个审核整改分支和独立 Git worktree。现在只保存进度，等报告返回后创建。** Worktree 是同一 Git 仓库的另一份工作目录，可让原工作区保留当前版本，并单独验证整改差异。

当前 main 的 HEAD 还是旧版。直接从 HEAD 创建 worktree，会漏掉尚未提交的 Rust 重写代码。因此先把核对过的当前源码和必要文档保存为审核前基线提交，再从该提交创建 worktree。提交时使用明确文件清单；宽泛的 accounts/ 忽略规则会漏掉新账号模块，必须核对全部 77 份 Rust 文件。编译缓存、私有数据和历史输出不作为源码版本纳入。

```text
当前暂停快照
    ↓ Gemini 报告到达，逐条核实
审核前基线提交
    ↓ 从同一基线创建 codex/gemini-review 分支和 worktree
最小整改 → 必要测试 → 整改版本
    ↓ 合并回当前主线
对比 R01–R05 → 接着完成旧版核心 → 再推进广告
```

1. 保存 Gemini 报告，检查它实际读过的文件和版本；逐条标注采纳、部分采纳或不采纳，并给出证据。Gemini 的建议不能自动新增需求。
2. 核对冻结清单和当前差异，建立审核前基线提交。保留现有修改，不执行清理或用旧 HEAD 覆盖工作区。
3. 从基线创建独立 worktree 与 codex/gemini-review 分支；在其中实施最小整改，并记录报告条目与提交的对应关系。
4. 完成必要验证，保存一个可回退的整改版本；集中安排一次最终安装验证，不把每次中间构建都交给用户安装。
5. 将通过验证的整改分支合并回主线；逐项对照本记录和机器状态，标明完成、保留、取消和新增剩余项，再继续开发。

上述是用户认可方向的接续方案，不是已经创建分支、worktree 或完成合并。本轮没有提交、推送、新建对话或创建 worktree。
