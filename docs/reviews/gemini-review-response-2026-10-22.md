## 1. 对用户关心的问题的结论

1. **资料去向。** 已审查源码中，尚未发现账号档案、聊天、Cookie 或令牌上传给项目方的路径。实际运行载荷验收仍待执行。
2. **远程修改。** 旧更新器会获取上游 main 并执行新版脚本。本机定时触发保持停用。旧手动 `update` 仍指向该上游。
3. **新增发现。** 时区响应在管理员授权前写入脚本。修复流程还会在特定条件下安装用户可写的服务配置。
4. **当前本机。** 已安装核心与仓库源码匹配，差异仅为五个安装配置字段。两份系统脚本和两份服务配置也与展开后的模板一致。
5. **本轮产出。** 完成文档修订和只读核对。Rust 实现、签名发布源、运行流量验收进入后续实施阶段。

### 2.1 时区风险的准确触发顺序

攻击者需要控制一个被采用的地理服务响应。返回值还需通过现有国家与 IP 条件。用户执行 `set-region` 后，脚本先把时区写入自身。

写入动作保存文本。若文本含有效 shell 命令替换语法，下一次普通脚本调用可能执行该语法。该阶段使用当前用户权限。取消管理员授权仍保留之前的脚本写入。

时区随后还进入管理员 shell。这个阶段需要系统授权。此前报告遗漏了用户态阶段，本次已更正。

### 2.2 用户可写 plist 的前置条件

攻击者需要先获得用户目录写入能力。旧更新器下载的恶意脚本可能提供这类前置能力。

`fix` 还要求代理、TUN 和出口检查通过。随后，系统服务查询需返回失败。用户批准管理员操作后，脚本才复制并注册该 plist。

本机该用户 plist 可写。两个系统服务目前均已注册。系统服务域的修改要求 root 权限，见本机 `/usr/share/man/man1/launchctl.1:35–37`。

### 2.3 重装判断的依据

本机 `/usr/share/man/man1/launchctl.1:107–110` 说明 disable 状态跨重启保留，需要 enable 后才可重新加载。

因此，当前安装器在同一用户域、同一服务标签下，仍受既有禁用状态约束。这一结论来自源码和系统文档。本轮实际重装次数为 0。

### 3.1 XPC 与签名能力

Gemini 关于 `xpc_connection_set_peer_code_signing_requirement` 的 macOS 12+ 判断有依据。本机 Apple SDK 声明和 Apple DTS 说明一致。方案继续以 macOS 13 为目标。[Apple DTS 说明](https://developer.apple.com/forums/thread/681053)

UI、普通权限核心和 mock helper 可以先做原型。真实 root helper 联调采用可验证的 Apple 签名身份。公开分发采用 Developer ID 签名和公证。各阶段分别登记身份与结果。

`AuthorizationCreate` 返回授权对象。特权执行仍需对应机制。首版交给系统 Installer 安装签名 PKG，再通过已安装 helper 完成固定操作。[Apple AuthorizationCreate](https://developer.apple.com/documentation/security/authorizationcreate(_:_:_:_:))

### 3.2 Tauri 更新能力与项目新增能力

核对的固定版本为 updater `v2.14.0`。其 `pubkey` 是单个公钥字段。`requireSignedVersion` 校验签名中的版本；`allowDowngrades` 控制常规降级行为。方案显式设定前者为 true、后者为 false。[固定版本配置](https://github.com/tauri-apps/plugins-workspace/blob/updater-v2.14.0/plugins/updater/src/config.rs)

完整发布元数据验签、过期判断、持久化发布序号与密钥恢复由项目补充。正常轮换采用旧密钥签名的桥接版本。密钥失效后，通过独立 Apple 签名、公证的离线安装包建立新信任。

这套恢复流程保留 Personal 的逐次确认，也保留 Public 的日常自动更新。发布者仍控制其签名程序的代码。密钥泄漏期间，旧客户端的信任配置仍需恢复。

### 3.3 广告的实际可见信息

静态整份清单减少应用附加的识别字段。服务端仍可看到出口地址、请求时间、协议元数据和请求的素材。选择性素材下载可能反映服务兴趣。

应用内下载验证每一跳。浏览器打开商家页面后，后续导航由浏览器与商家执行。验收分别记录这两条路径。
