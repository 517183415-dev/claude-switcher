## 2. 类型生成、协议模型与构建顺序

### 2.1 类型生成

Rust domain 类型是唯一源。独立导出命令在 `check` 和 `build` 前运行。导出工具放在无 Tauri 构建依赖的 crate 或独立 xtask，避免形成构建循环。

顺序固定为：Rust 类型导出 → 前端类型检查 → 前端构建 → Tauri 构建 → 实际窗口验证。

P0 保留锁定 ts-rs 版本，依据其真实 API 修复调用。生成物策略在 P0 固定：提交生成物时，CI 检查重新生成后零差异；忽略生成物时，每个干净构建入口必须先生成。

当前 Vite 已构建通过。`import type` 在打包时可以被移除，因此类型缺失应通过干净 `check` 实测。既有证据指向 build.rs 编译失败；不要把时序风险写成所有 Vite 构建必然失败。

### 2.2 签名封装和重复字段

签名绑定原始 payload 字节。接收方先检查封装大小和格式，再验签，最后按固定 schema 解析 payload。签名覆盖版本、环境、key ID 及全部业务字段。

所有层级使用固定结构体，并拒绝未知字段和重复 JSON 字段。动态 map 若确有需要，使用显式重复键检测。使用同一个经过校验的对象驱动后续操作。

广告清单固定三个 slot 分组。每个分组最多两条 campaign，所有 `campaign_id` 唯一，同一 slot 的区间互斥。两个 campaign 可以属于同一个 slot；三组的 slot ID 必须唯一完整。空位以空 campaign 列表表达。

P0-03 必须补齐三个占位模块，并提供正负 fixture。只修编译错误后运行零业务用例，任务状态保持待完成。

## 3. 软件更新的验签、安装和恢复

### 3.1 三层校验与字段映射

| 层级 | 格式与密钥 | 校验对象 |
| --- | --- | --- |
| 发布元数据 | Ed25519 原始 payload 字节签名 | edition/channel/OS/arch、version、sequence、有效期、具名 app/helper artifacts 的 URL/大小/SHA256/版本/身份、app Minisign 签名、组件兼容范围 |
| 更新工件 | Tauri updater 2.14.0 的 Minisign 格式；独立工件公钥 | 下载字节与受签名保护的版本注释 |
| macOS 身份 | Apple 代码签名；PKG 使用 Installer 身份 | 应用/helper 的发布身份、安装包、公证与票据 |

发布元数据使用具名 `artifacts.app` 与可选 `artifacts.helper_pkg`。每项绑定版本、URL、大小、SHA256 和身份要求。app 核对预期 Team ID/Bundle ID；PKG 核对 Installer 身份，并核对 payload helper 的代码身份。共享 helper 变更须满足已登记客户端的兼容合同。

元数据与 Minisign 的签名格式分别处理。各发行配置固定其元数据公钥、工件公钥、端点和允许的身份组合。广告再使用独立内容公钥。测试密钥只用于 fixture。

```text
固定更新入口
  → 原始元数据验签、schema、发行/平台/时间/序号
  → 生成已验证候选对象并记录其 payload 哈希
  → 下载唯一绑定的工件，核对体积与 SHA256
  → Minisign 验签，核对签名版本与元数据版本
  → Claude 退出 + 写入空闲 + guardian/helper 兼容
  → 安装、重启、健康确认 / 本地兼容回退
```

Rust 适配层持有已验证候选对象。若插件再次获取网络响应，逐字段核对 URL、版本和签名与候选对象一致。安装使用同一份已验字节，避免验证后重新下载引起替换。

`requireSignedVersion=true`、`allowDowngrades=false` 均为锁定 2.14.0 的真实配置。自定义版本比较器会覆盖默认比较规则；首版沿用默认前进规则。工程若需要比较器，先补对应契约与负向用例。

macOS updater 工件为 `.app.tar.gz`。helper 的签名 PKG 由独立安装协调器交给系统 Installer。需要新 helper 时，先验证兼容组合和授权结果，再提交应用升级。取消授权后保留原组合。

参考：[固定版本配置](https://github.com/tauri-apps/plugins-workspace/blob/44293a5722efcaf27060504e63b17aeba721b40f/plugins/updater/src/config.rs#L153-L173)、[安装前验证](https://github.com/tauri-apps/plugins-workspace/blob/44293a5722efcaf27060504e63b17aeba721b40f/plugins/updater/src/updater.rs#L895-L925)、[Minisign 版本校验](https://github.com/tauri-apps/plugins-workspace/blob/44293a5722efcaf27060504e63b17aeba721b40f/plugins/updater/src/updater.rs#L1893-L1967)。

### 3.2 最高序号与故障版本隔离

本机持久化 `highest_verified_sequence`、对应 payload 哈希、当前候选、安装事务及故障版本记录。以 edition/channel/OS/arch 分区。有效较高序号通过完整验签和语义校验后，原子提交认证记录。

同序号、同 payload 允许幂等恢复。安装或安装后健康检查失败时，保存 `blocked_releases`。记录 sequence、version、组件、artifact SHA256、组件组合、失败阶段、原因码、尝试时间与回退结果。应用健康失败隔离 app；helper 或组合失败隔离对应组件/兼容组合。授权取消记录 CANCELLED，保留可重试候选。

后续自动轮询跳过已隔离工件或组件组合。更高序号若仍引用同一失败字节，也保持隔离。新工件通过全部校验后可成为下一候选。本人查看失败原因并显式重试时，单次授权只作用于指定候选。

暂时下载失败进入退避；身份、签名或哈希失败拒绝该候选；安装/健康失败进入持久隔离。三类错误分别展示。自动回退只恢复已验证的本地兼容版本，并保留最高序号与故障记录。

正常密钥轮换使用桥接版本。独立 Apple 签名、公证的离线恢复包用于应急建立新信任。保持 Personal 手动确认与 Public 默认 12 小时检查策略。

## 4. 双发行服务所有权与 XPC

### 4.1 唯一活动拥有者

Personal/Public 保持独立 Bundle ID、配置、端点、密钥和更新任务。同一 UID、同一规范化 Claude 数据目标共享写入锁与活动 guardian 租约。

租约记录 owner edition、应用路径/签名身份、协议版本、activation generation 和心跳。用户目录中的记录用于协调；root helper 的授权依据为已认证连接与本机激活状态。

第二个发行打开时显示当前拥有者。检查和只读页面可用；启动、切换、修复等写入操作交给活动拥有者，或先完成明确的接管事务。

交接事务先按固定顺序取得共享生命周期锁、账号写入锁。在锁内重新核对拥有者、代次、Claude 退出状态和待恢复事务，再执行：保存交接意图 → 停旧 guardian 并撤销租约 → 注册/启动新 guardian → 身份与心跳握手 → 提交新代次 → 恢复启动入口。竞争者只读取已提交代次。

交接失败先恢复旧拥有者。恢复失败时保留日志和快照，启动入口显示恢复动作。非活动发行的更新也遵守 Claude 退出和写入空闲条件；修改共享 guardian/helper 前，取得相同锁及活动拥有者协调许可。跨 UID 的系统 helper 修改由 root helper 内部全局生命周期锁串行化；固定顺序为客户端生命周期锁 → 账号锁 → helper 全局锁，helper 不反向等待客户端锁。

稳态只有一个注册并工作的 guardian。交接期间允许短暂无守护，启动入口保持等待。P0 对 SMAppService 的跨 Bundle 注册/注销、崩溃恢复和残留注册做实测。若该接口无法满足唯一实例条件，G3 提交共享 guardian 宿主 ADR 后固定替代方式。

至少验收：两发行同时启动/接管、接管与自动更新并发、旧 guardian 已停而新注册失败、旧应用退出但 guardian 存活、交接中断、重复注册、协议跨版本、系统重启、快速用户切换、两 UID 同时登录。旧 Bash 守护与新 guardian 的最终交接放在受控迁移任务。

### 4.2 身份与用户授权

每条特权请求验证收到消息的代码身份。requirement 使用明确的 `(Team ID, Bundle ID, 角色)` 允许组合，分别列出 Personal/Public 的实际客户端。CLI 若直接调用 helper，应有独立受签名身份及允许操作；普通测试程序没有生产特权。

`xpc_connection_set_peer_code_signing_requirement` 负责收到消息的签名约束。需要手动验证时，使用收到的 XPC 消息建立 SecCode，再应用签名要求。以 PID 重新寻找进程仅作诊断用途。

`xpc_connection_get_euid` 提供连接建立时的 EUID。root helper 另外核对激活 owner UID、登录会话、请求角色和固定操作。P0 验证每消息 audit token 的 UID 与连接、租约一致性；避免把连接 EUID 描述成已经验证的每消息 UID。

快速用户切换按会话规则处理。系统范围的时区/网络修改要求当前受授权活动会话；普通用户的 guardian 只管理自己 UID 的 Claude。注销或会话变更撤销旧激活状态。

PR-13 身份矩阵包括：合法客户端、同 Team 错 Bundle、同 Bundle 错 Team、其他 UID、临时签名、协议错误、过期代次、错误角色、任意 plist/路径/命令、连接存续期间的身份变化。

参考：[Apple XPC 签名约束](https://developer.apple.com/documentation/xpc/xpc_connection_set_peer_code_signing_requirement(_:_:))、[消息身份](https://developer.apple.com/documentation/security/seccodecreatewithxpcmessage(_:_:_:))、[连接 EUID](https://developer.apple.com/documentation/xpc/xpc_connection_get_euid(_:))。

## 5. 账号事务与目录外依赖

### 5.1 同卷交换与持久化

P0 首选验证 `renameatx_np(..., RENAME_SWAP)` 或等价 `renamex_np`。先核对同卷与卷能力，记录文件系统、设备、目录身份和失败返回。目标目录通过固定根路径与规范化校验；拒绝将符号链接作为受管理根目录。

事务记录至少包含 operation ID、账号 ID、源/目标目录身份、快照路径、staging 路径、前后 current、阶段及数据清单摘要。

| 检查点 | 动作 | 中断后的处理 |
| --- | --- | --- |
| prepared | 退出 Claude；建立可验证快照；准备目标 staging | 当前目录保持有效；识别并清理未提交暂存 |
| swap_intent | 持久化日志、文件和必要目录元数据 | 核对实际目录身份，判断交换是否发生 |
| swapped | 原子交换；再次核对目录身份并同步父目录 | 按日志选择提交或恢复，保留原目录 |
| current_committed | 单次原子替换 v2/active-state.json 提交对象，随后生成兼容 current 镜像 | 提交对象指向已验证目标；重建镜像并继续收尾 |
| completed | 写入完成记录；保留可用快照后清理暂存 | 下一操作可进入 |

`v2/active-state.json` 是 Rust 当前账号与提交代次的唯一权威对象。它保存 current、operation ID、目录身份与必要 v2 状态。旧 `current` 文件作为兼容镜像在提交后更新；Rust 从权威对象重建它。旧程序在 Rust 拥有资料期间保持停用。首次导入缺少权威对象时，从已验证旧 current/资料状态建立它。

恢复规则：未交换且无新提交则保持旧状态；已交换且目标身份匹配、尚未提交则完成提交；已提交且目标身份匹配则重放镜像和收尾；日志损坏、目录身份冲突或目标验证失败时保留全部原目录与快照，进入受控恢复入口。每一分支分别注入中断。

G1/G3 在 ADR 中列出每个落盘点的 `sync_all`/`fsync` 调用与错误处理。目标硬件需要更强保证时评估 `F_FULLFSYNC`。每个失败返回都进入可恢复状态。交换 API 不支持时保留原资料，提交备选事务 ADR 后再启用该平台。

F-05/F-06 覆盖文件内容、权限、xattr、目录身份、磁盘不足、跨卷导入、各检查点进程终止及重启恢复。进程终止、系统重启和真实断电使用独立证据列。仅执行前两项时，断电列保留 NOT_RUN。

参考：[Apple fsync 手册](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html)。RENAME_SWAP 的卷要求以目标 SDK 和本机 `renamex_np(2)` 手册记录留证。

### 5.2 Keychain 调查方法

safeStorage/keytar 字符串只作为调查线索。P0-05b 建立逐项证据表：Claude 版本/签名、数据位置、项类型、所属应用、ACL、是否共享、是否账号专属、所需动作与恢复依据。

先检索相关代码用法和限定范围的条目元数据。`svce`、`acct` 也可能包含邮箱或用户标识；公开报告只保留脱敏值。查询明确使用属性返回，关闭 secret 数据返回。访问授权由系统界面处理。

依赖分别判定为共享加密材料、账号专属凭据、设备/Passkey 状态。每项选择保持原位、受控迁移或重新登录。具体 Keychain 项名和策略以证据固定。

合成事务在 P0-05a 通过后继续开发。真实 A 迁移要求 P0-05b 与备份恢复通过。真实 A→B→A 另需第二个可用账号。当前只有 A 时，F-09 保持 WAIT。

## 6. 广告内容、图片、时间与商家链接

### 6.1 三广告位与图片预算

固定顺序：`residential_broadband` 美国家庭宽带、`account_service` 注册好的账号、`kyc_service` KYC 服务。每位当前期/下一期独立编辑；最多六条 campaign。

图片流程：接收有界字节 → 核对签名清单中的哈希/格式 → 在分配像素缓冲前检查文件头 → 有界解码 → 验证实际尺寸 → 本地展示。

单图压缩字节 ≤1 MiB，宽×高 ≤2,000,000 像素，解码工作内存 ≤16 MiB。乘法使用溢出检查。对 PNG 的 `acTL`、WebP 的动画标志和动画 chunk 显式拒绝；只解第一帧的行为不满足静态图片合同。

解码器须证明能在分配前限制尺寸和工作预算。若库接口无法覆盖内部临时分配，采用受限解码进程并验证终止行为，再通过 PR-10。压缩数据、解码数据和 UI 纹理分别计量；并发解码上限为 1，下一期素材采用有界缓存。

PR-10 增补：伪装格式、截断文件、APNG、动态 WebP、超大尺寸、小文件高内存、整数溢出、哈希错配、超时、decoder 资源越限。失败素材显示本地占位，主操作继续可用。

### 6.2 刷新与传播口径

固定下次计划时间为 `last_success_at + 15min + jitter`，jitter 每个周期取一次 0–60 秒并保存。运行期间用包含睡眠时间的单调时钟计算剩余时间；UTC 用于持久化和排期。

唤醒时已到期立即补查；尚未到期按剩余时间调度。进程重启先恢复计划时间并验证时钟。调度不会从每次唤醒重新累计完整 15 分钟。一次请求在途时合并重复触发。

成功要求完整传输、签名、序号、schema 和有效期检查。失败按 1/5/15/30/60 分钟退避，之后每 60 分钟；退避记录与正常周期分别维护，成功后重新建立周期。

20 分钟传播指标从发布端公开回读成功开始计时。测试条件为客户端持续运行、广告开启、网络及内容源正常、首轮刷新成功。预算为轮询 ≤15 分钟、jitter ≤1 分钟、CDN ≤1 分钟、传输/校验/展示 ≤3 分钟。AD-05 以端到端实测为准。

网络失败、休眠和退出另外记录恢复延迟。一次周期包含重试时，报告实际延迟及原因。上线宣传使用同一测量条件。

暂停在下一次成功刷新后生效。离线缓存到期为 `min(last_success+24h, campaign.ends_at, manifest.expires_at)`。发布端展示“在线刷新采用；离线最长按现有缓存期限展示”。当前方案保持 24 小时缓存合同。

### 6.3 时钟异常与恢复

P0 使用确定性时钟 fixture。进程内比较 UTC 与包含睡眠时间的单调计时；跨启动保存最后可信 UTC、boot/session 标识和最高内容序号。显著回拨、可信时间冲突或计时来源异常进入 `clock_untrusted`，收起广告，更新安装等待时间复核。

恢复策略为项目合同，HTTP Date 只提供辅助时间证据。使用同一自控产品域名的固定 `/time.json` 恢复入口，查询参数为空，配置并实测 `Cache-Control: no-store` 与 CDN 绕过。Date 为必需字段；Age 缺失的直源响应可接受，Age 存在时要求为 0。普通可缓存清单的 Date 只作诊断线索。该端点进入外发用途清单。

默认参数：两次有效采样间隔 30–120 秒、RTT ≤5 秒、本机 UTC 与候选服务时间偏差 ≤5 分钟。核对系统校时状态、两次 Date 的推进与单调间隔一致，先形成候选可信时间，再用该候选时间检查最新签名内容的有效期及持久序号。全部通过后一次性提交恢复状态。

缺失 Date、缓存策略冲突、服务时间停滞或系统时间仍异常时保持等待，并显示“检查系统日期后重新校验”。系统时间导致 TLS 失败时，由用户修正系统日期后重试，TLS 验证保持启用。P0 实测确认阈值与缓存行为；调整参数写入 ADR。恢复后重新计算缓存/排期，保留最高序号和失败版本记录。

时间恢复 fixture 覆盖直源无 Age、缓存带 Age、两次采样冲突、校时后恢复、TLS 日期错误及回拨后旧内容重放。

所有广告关闭时，时间恢复流程也保持零广告请求。用户主动检查软件更新或运营回读可分别提供相应通道的时间证据。

参考：[HTTP Date](https://www.rfc-editor.org/rfc/rfc9110.html#section-6.6.1)、[Age](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.1)、[缓存年龄](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.3)。

### 6.4 商家链接与内容源

产品内容源：清单、图片和软件工件下载域名由发行配置固定。每次重定向继续校验 HTTPS、域名和路径，最多三跳。

商家落地页：域名和 HTTPS 目标随签名广告发布。商家或目标域名变化后，首次点击再次显示商家与完整域名。日常更换商家通过广告发布完成；内容源、公钥和客户端模板变更走软件发布。

商家 URL 使用统一解析器。拒绝 userinfo、IP 字面量、localhost、非公开主机形式和非 443 端口。规范化 IDN，并同时显示可读域名和 ASCII 主机名。公开活动参数采用明确字段；保持账号、设备标识和用户资料零附加。

点击确认绑定 `merchant_id + normalized_host`。链接来自当前有效签名清单。系统浏览器接管后，导航行为单独记录。首版不引入广告点击上报服务。

AD-02/AD-09 增补：商家 A 改为 B 后，应用版本和程序哈希保持一致；新域名重新确认；清单和素材仍仅访问固定内容源。

### 6.5 托管验收

### 8.3 长期观察

48 小时基础观察从安装健康确认后计时；随后开始连续 7 天日常使用观察。记录 build/配置摘要、睡眠、唤醒、重启、换网、代理重连、急停、手动/自动更新及资料恢复。

正常睡眠不重置日历观察，但活动时段须覆盖上述事件。产品故障或影响业务的修复后，相关观察阶段从修复构建重新计时。缺日志或停止采集时记录中断并补足证据。只改文档可延续观察，并登记差异。
