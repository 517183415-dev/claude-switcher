## 4. 完整适用核心测试与 DRY/SOLID

“完整适用”指本次支持合同的分支均有可执行验证，不以方法总数或一条绿色命令代替。先列测试清单，再运行；发现系统调用缺口时修负责层边界，不能跳过用例后宣称完整。

| 责任边界 | 必测集合 | 复用与最小改动原则 |
| --- | --- | --- |
| domain/core检查、网络与账号 | DTO严格解析；14项及启动门禁；显式代理/STUN；current/v2；A/B事务；journal全部持久检查点；生命周期锁与停止独立 | GUI/CLI/guardian共用现有策略与核心函数。只在文件、进程、网络、时钟等真实边界注入假对象；不复制一套“测试业务”。 |
| 修复、helper、安装与守护 | 固定动作参数；owner/角色/签名；授权取消；一次修复后全检；恢复幂等；组件兼容；心跳/事件/十秒兜底；root小时校时 | 高权限代码保持固定职责。业务层依赖小接口；用户guardian不重新获得直接校时；安装状态不被普通请求登记。 |
| 更新与广告读取 | SourceLocal/DeveloperId分支；原始字节验签和严格schema；工件绑定；调度、失败抑制、时钟；图片/清单限额；三槽缓存/排期/零请求 | 共用既有有界解析、验签、HTTP策略和时钟；不同信任模式不靠布尔散落复制流程，也不为未来扩展新建框架。 |
| Personal发布与恢复 | preview/production；CAS/pending/终态；上限包含边界；历史与素材引用；两次确认/重启；加密备份与认证续发 | 把发布状态、存储、密钥与UI职责保持分开；复用现有publication锁和认证current路径；Public不编译写能力。 |
| 桌面与交付 | 两版前端测试、类型、生成DTO差异、成功/拒绝IPC、中文状态/取消/键盘、包注册与发行标识 | 只在装配点选择测试边界，commands及生产核心保持同一路径。测试构建入口不能进入正式包；仅为已发现缺口引入窄接缝。 |

运行前审查所有 Rust/Python/Node 测试的子进程、绝对路径、用户目录、Keychain、XPC、网络与系统命令。历史 R11 sysctl、R08 rustup 下载偏差继续保留。不得直接执行未审查的全量 `cargo test --workspace`。待整个适用集合已隔离后，才能使用对应集合命令；无法安全覆盖的具体用例单列阻塞。

使用现有直接Rust工具链、锁文件、缓存和前端依赖，Cargo使用 `--offline --locked`。前端运行现有 `npm test`、`npm run check`；生成类型只提交相关差异。执行适用Rust/Python回归、fmt、typecheck、lint/Clippy和两版离线构建；不安装或升级依赖。缺少覆盖率工具时不安装；记录分支清单覆盖，不能报告未计算的百分比。

每个新 bug 走同一回归流程：记录触发输入与错误结果；保留在修复前失败的最小用例；在负责层最小修复；重跑失败用例及受影响消费者；最后运行完整适用核心集合。用例验证用户可见结果和资料/权限等不变量，不只镜像实现。测试环境错误单列为测试工具问题，修正后保留首轮失败与有效重跑，不能冒充产品 bug 已修。

P1 安全边界 → P2 核心回归 → P3 原生与运营 → P4 固定候选 → P5 分层交付
                  │                           │              │

短期测量必须遵循工程 §8.1：同一release启动10次；反馈20次；正常/超时/换网检查各10次；guardian空闲/复制/CPU压力/唤醒各5次；预热5min后采样30min。报告首次启动、缓存条件、p95、CPU/RSS与证据完整性。固定阈值只用于合同已有指标，不发明新的性能预算。

实际稳定性至少需要先48小时再7天。Public可信更新实际12小时和广告健康在线20分钟分别留证。测试期间的加速时钟、CPU压测或重启次数不等于这些时间。缺少设备、源或授权时，交付已完成阶段并列精确阻塞，不把其余35项合并标PASS。
