客户端入口 `ad_runtime.rs:189–230` 分发行写 `v2/{personal,public}/ads` 自己的缓存，读取发布树由 `ad_runtime/local.rs:35–95,102–114` 完成。LocalFetcher 只读 `production/`，无写文件 API；`:45–66` 使用本机公开验证材料。Public 只读是产品代码/IPC 边界，两发行仍以同一用户 UID 运行，并非 macOS 用户隔离：目录 0700 并不能阻止任意同 UID 外部程序修改这些文件，不能夸大此边界。

### 3. 没有可达的多云、专用时间服务或点击统计

- 唯一生产 ObjectStore 实现是 `publisher/local_store.rs:118–200`；另一个 MemoryStore 在 `publisher/tests.rs:77–193`。`protocol.rs:24–41` 是小型单适配器接口，不足以证明预建多云架构。
- `ad_runtime.rs:29–33` 的远程 `ContentPins::production()` 返回 None。虽然 HTTPS Fetcher 仍编译在 `:99–157`，当前真实构造只能走本机 pins，`:412–419` 的本机分支选择 LocalFetcher。`local.rs:4` 的 `https://local-ads.example.com/` 只是内部路由命名，不会真的请求此域名；`:72–95` 把 URL 转成固定文件相对键。
- `security.rs:12–13` 的 preview/production credential 是空闲的未来字段；实际生成入口 `publisher_commands.rs:157` 传两个空 Vec，LocalStore `:122–124` 不需要凭据。它们可以后置清理，不能据此声称用户现在被要求提供云账号。
- 广告时间依赖本地 `ClockSample/ClockState`（`ad_runtime.rs:232–269,399–404,491–514`），本批没有专用 time.json 请求/服务。时间模块本身由 updates 批审查。
- `ads.rs:133–158` 是商家/域名确认记忆，`ad_runtime.rs:567–600` 是短时确认挑战及最多三个 consent 的持久化，不记录点击次数或发送统计；`bridge.rs:479–508` 最终把当前校验出的 HTTPS URL 交系统浏览器。不能把 consent 命名里的 click 认定为点击统计。
- 广告 channel 是 Preview/Production（`switcher-domain/src/ads.rs:6–11`），不是第三个试用产品发行；不要混淆 channel、Personal/Public 与 SourceLocal。

### 4. 端到端验证与核心功能解耦

`ads.rs:161–244` 检查 schema/channel/key_id/序号/时效/唯一三个广告位/每位最多两期/不重叠/文本/URL/图像元数据，签名先由 shared signed 模块验证。`ad_runtime.rs:443–453` 在素材处理前记住认证最高序号；`:500–514` 全部所需素材通过后才接受可展示缓存。`Persistent.sequence` 和 `AdCache.highest_revision` 的区别有实际意义：前者是已经认证的反重放水位，后者是素材完整的可展示版本；不能简单当重复字段删掉。

`ad_runtime.rs:292–325` 显示前再次检查时钟、最高序号、本机 current 摘要、用户开关、活动排期和缓存图片；本机 current 删除或变更会使旧广告立即不可显示。`bridge.rs:173–181` 捕获广告错误并折叠广告，继续组装工作台，没发现“坏广告直接阻断账号工作台”的错误传播。共享 v2 锁的竞争影响应与主审锁/账号批合并评估，本批不另造重复问题。

## 二、确定问题（按本批优先级）

### ADS-01 / P2：导出的合法备份可能被自己的恢复入口拒绝，前后端容量契约不一致

**生产证据与链路**：

1. `publisher/backup.rs:10,30–33,62–69` 采用 64 MiB 完整备份上限；header 为 60 字节，加 16 字节 AEAD tag。
2. `publisher/mod.rs:874–897` 把草稿、全部历史、全部导入素材和 secrets 序列化，允许 `backup::LIMIT-76` 的明文，再导出到该 64 MiB 格式。`ASSET_LIMIT=128`（`:71,465–470`）且单图最多 1 MiB，所以超过 32 MiB 的合规导出是可达状态，不是单清单 256 KiB 上限能排除的情况。
3. `publisher_commands.rs:165–189` 把这样的备份写文件并报告成功；恢复入口 `:192–199` 却先拒绝 `bytes.len()>32*1024*1024`。
4. `apps/desktop/src/pages/Operations.svelte:40` 前端接受到 64 MiB，明确提示 64 MiB；因此 32–64 MiB 用户备份会经过 UI 选择，随后在真正恢复前被拒绝。

**影响**：已成功导出的备份无法通过官方恢复入口恢复；灾难恢复时才发现最危险。当前源码测试只用极小 PNG，`publisher/tests.rs:425–479,664–761` 没覆盖此边界；它们直接调用 Publisher 方法，也绕过了不同上限的 Tauri command。

**最小修复**：恢复命令复用 `publisher::backup::LIMIT`，前端显示同一生成/导出的常量或统一协议上限；选择保留 64 MiB 时，不能只把导出改成 32 MiB 来让既有 32–64 MiB 备份永久失去入口。保留 AEAD 和 KDF 资源上限。

**删除范围/风险**：删除 32 MiB 的重复 magic number，不删加密、大小门禁、Keychain、私有权限；已有大备份需兼容。验证应覆盖 32 MiB 上下、64 MiB 上限及真正 IPC 恢复路径，允许使用合成合法备份和内存 Vault，不需要真实 Keychain。

**同类 UI 契约差异（可与桌面批合并）**：Operations.svelte:34 允许原图到 8 MiB，`publisher_commands.rs:42–45` 和 `ads.rs:551–553` 实际只接收 1 MiB。用户会看到“导入前原图 <=8 MiB”但 1–8 MiB 必定拒绝。若原意是输入 8 MiB、归一化输出 1 MiB，应把输入/输出上限明确区分并保持解码像素/内存限制；否则把 UI 同步成 1 MiB。它比备份恢复不一致轻，应作为同一容量契约整理项而非夸大安全漏洞。

**置信度**：高，静态确定；未执行动态大备份测试。

### ADS-02 / P2：已提交的 pending 缺少终止/修复出口，过期或永久缺素材可把整个运营锁死

**生产链**：`publisher_commands.rs:116–143 → Publisher::publish_with`。pending 在 `publisher/mod.rs:720–727` 写入，提交前又保存 CommitUnknown（`:775–784`）。再次发布时，只要 current 等于 pending.wire，`:741–750` 立即进入 finish_readback，不走重新上传路径 `:764–775`。finish_readback 任意失败都设 ReadbackFailed（`:796–801`）；`:821–829` 用“当前 now”验完整清单时效，`:833–846` 要版本和所有素材回读成功。

**两个具体、生产逻辑确定的触发场景**：

- 提交已成功，但后续回读/本地状态持久化未完成，用户超过 90 天才重新打开（有效期在 `:704–707` 设为 90 天，`ads.rs:179–185` 拒绝过期）。current 仍等于 pending，每次重试都走当前时间验签/校验，得到 manifest_time → ReadbackFailed；无时间可恢复为非过期状态。
- current 已提交后，版本文件或发布素材永久缺失，但 Publisher 私有素材仍然完整。每次重试 current 匹配便直接回读失败，永远不执行 put_immutable 去补齐缺对象。正常“再发布同一成功版本”的幂等分支 `:661–677` 也会创建这种 pending，再走同一出口。

**封锁范围**：`draft_save :391–399` 拒绝所有非 Conflict pending；`pause :431–438` 和 `restore_history :440–450` 复用 draft_save；`restore_backup :899–912` 也拒绝非 Conflict pending。UI 暂停、改稿、历史恢复、备份恢复均不能解决，单靠重试无法恢复。这是恢复状态机的缺口，不是必须删除防重放水位的理由。

**现有测试的边界**：`publisher/tests.rs:347–423` 测试的是短期结果未知、暂时损坏回读，然后测试主动让 store 恢复正常；没有让 pending 真正过期，也没有让 current 保持匹配而版本/素材永久缺失并测试修复。不可把这些测试名称当作覆盖所有 pending 恢复。

**最小修复**：把“认证某次提交是否已经发生”与“该清单当前能否展示”分开。回查已提交版本可以在签发时刻验证结构/签名并保留最高序号，再将过期提交标为已完成/已终止，允许创建更高序号新稿；不能把过期广告重新展示。对于匹配 current 但缺不可变对象，允许从已经验证的本地素材/同一 pending.wire 幂等补齐，再回读。若确认无法修复，提供经过 current/ETag 复核的明确终止入口，保留审计/水位，允许发布新的暂停版本。

**删除范围/风险**：删的是无出口的统一 gate / 直接回读捷径，不是 CAS、签名、反重放或 CommitUnknown。不能无条件“清 pending 并忘记序号”，否则会重复提交或回滚。测试应构造已提交后过期、current 相同但资产/版本缺失、修复期间另一更高版本出现，验证水位保持、恢复出口及暂停可用。

**置信度**：高，静态状态转换可证明；触发需要未完成提交跨过有效期或发布对象丢失，本轮未动态复现。

### ADS-03 / P2：历史/素材只增长，无正常回收入口；达到硬上限后连暂停新版本也不能发布

**证据**：`publisher/mod.rs:69–71` 固定历史 256 条/素材 128 个；`:452–471` 每个新图都加入 assets，重复 hash 才不增长；`:440–450` 只恢复历史，不删除历史。发布 `:649–652` 在任何新 pending 前拒绝 `history.len()>=256`，且早于幂等检查 `:653–679`；成功回读 `:857–866` 只 push 历史，未提供 prune 操作。14 文件及 Personal 注册入口没有历史归档、资产删除或回收命令。

**影响**：256 次不同成功发布（预览和正式共用 history）后无法再正常发布；“全部暂停”可以写草稿，但发布暂停版也被该门禁拒绝。128 张不同导入图片后，即使从草稿删掉无用 campaign，仍无法导入第 129 张。恢复较老备份可能减少本机条目，不能视为正常保留策略。资产全部纳入备份，使容量在达到 128 个前就可能超过 64 MiB 序列化上限，导致 export_backup 失败。

**最小修复**：保留上限，增加简单而可理解的保留/归档策略或显式整理入口。历史裁剪与反重放水位分离，永不降低 `sequences`；只回收既非当前/草稿/pending、又非保留历史引用的素材。先确保用户可备份/归档旧历史，禁止为“清理”任意删账号或活动广告资料。无需新数据库、云归档平台或后台服务。

**删除范围/风险**：合并只增长索引和无出口容量 gate，不能改成无限容量，也不能不检查引用直接删素材。验证只需小容量参数化到阈值或合成状态：达到历史上限后仍可安全暂停/续发，整理不会降低水位或破坏恢复引用。

**置信度**：高；是确定的有限运行寿命限制，频率取决于实际运营。

## 三、条件风险及需明确的恢复适用范围

### ADS-C01：加密备份能恢复发布者草稿，却不能独立重建曾发布过的空发布树

`restore_backup` 保存备份中的序号，并与本机水位取高（`publisher/mod.rs:952–958`），设 `recovery_required=true`（`:959`）。正式再发布先调用 read_remote（`:643–648`）；该函数若 current 不存在且对应 sequence.highest 非零，直接拒绝 `remote_current_missing_after_authenticated_release`（`:614–617`）。备份没有整个 local-ads 发布树，导出只收 Publisher 的 state/assets/secrets（`:874–895`）。因此备份若是在至少一次正式发布后产生，恢复到另一台电脑/全新应用根，或 local-ads/production/current.json 丢失，就不能通过该发布入口恢复运营。

现有“fresh installation”测试 `publisher/tests.rs:744–761` 只新建 restored-drafts，继续复用原来的 `store` 和原本 current。它验证“草稿目录新建 + 发布源仍在”，不验证“完整发布树也全新”。README:50 的文字实际写的是“未配置密钥的新草稿目录”，不能把它放大成已证明跨机器灾难恢复。UI `publisher_commands.rs:205–208` 告知再次发布会补齐素材，也没解释 current 必须还在。

**定性**：拒绝水位消失是合理的防回滚默认；但如果“完整备份与恢复”包括仅凭备份重建本机运营，这是确定的功能缺口。需求文件主审应判定承诺范围；不要把缺失 current 直接无条件当作首次发布。

**最小处理**：明确现有恢复前提，或在验证备份和私钥后提供显式“重建空的本机发布目录”流程，沿用保存的水位，以更高序号签发新 release，不把旧版当前内容原样降级回放。可先从现有 immutable version 恢复 current，并验证它不低于本机水位；没有可信材料时保留拒绝。测试要用两个完全不同应用根、已发布后导出的备份，以及 current 缺失/损坏场景。

### ADS-C02：暂停仍依赖已停用广告的素材完整性

`pause :431–438` 只把 slot.enabled 设 false，保留 campaign。新版本发布 `:710–712`、上传 `:765–774`、回读 `:839–846` 都遍历所有 campaign，未跳过 disabled slot/campaign。若发布者素材或发布对象损坏/丢失，“全部暂停”仍可能失败；客户端本来在 `ad_runtime.rs:454–462` 会跳过 disabled 内容。

暂停是“生成草稿、需再发布”的语义，Operations.svelte:36 和 publisher README:13 已明确说明，不能单凭按钮叫“暂停”就报告其应立即自动投放。但事故处置仍需要在素材不完整时发布无广告的签名新清单。最小方式是暂停发布生成不依赖素材的 disabled/empty 清单，同时把原稿留在历史，或在发布/回读中明确 inactive 对象无需齐全；保持正常广告素材验证。可与 ADS-02 的恢复出口设计一起处理，避免重复新增一套状态机。

### ADS-C03：极端磁盘提交错误需要明确结果未知，不能将所有原子写错误解释为未生效

`storage.rs:218–256` 明确 rename 是 commit point，随后父目录 fsync 可失败。LocalStore `:197–198` 正确返回 OutcomeUnknown；备份 active 指针切换 `publisher/mod.rs:1000–1009` 也会回读，匹配时同步内存并继续报告持久化错误。这些处理应保留。

普通 Publisher.persist `:301–308` 只在整个 atomic_write 成功后更新内存；发生 rename 后 fsync 失败时该次命令报错，但磁盘可能已生效。生产 `with_publisher` 每个命令重新打开，所以后续命令通常会读回新状态，不宜据此直接报告永久状态损坏。仍应在故障验证中覆盖“写盘报错后重新打开读到新稿/新pending”的结果未知提示，不能向用户保证失败就完全没修改。无需引入全新日志系统。

## 五、已有测试、证据缺口与最小整改次序

## 核心结论与可达性

1. 产品版本与安装信任大体是两个维度。UpdateSchedule 按 Personal/Public 决定自动性（updates.rs 897–941）；远程执行入口另通过 InstallRecord.developer_team 拒绝 SourceLocal（update_runtime.rs 385–388、685–697；guardian.rs 1163–1170）。Public+SourceLocal 不自动更新符合例外，不能据此删掉 Public+DeveloperId 的远程更新要求。
2. 当前唯一生产 release pins 函数固定返回 None（update_runtime.rs 52–56），new 91–103 据此不配置远程入口，main.rs 187–193 也不会注册 updater 插件。远程元数据请求、下载、Apple核验及安装协调器代码存在，但当前正常构建不可达。它们的安全/可用性缺陷应标为“实现可证、待配置正式远程通道后触发”，不能写成当前本地版已经在联网更新。
3. 日常 launch 没有本组代码设置的 clock/TTL 门槛。本组 clock 用于广告/更新共享的签名内容有效期连续性，不能将其概括为“启动必须可信时间”。time.rs 127–178 使用本地 UTC、mach_continuous_time 与 bootsessionuuid；没有专用时间服务、HTTP Date 或新的远程时钟平台。
4. “global lock merges duplicate processes” 测试的实际保证是重复任务抢锁失败，不是合并或回收子进程。更新事务具有真正的跨进程排斥；guardian 的 Child 生命周期仍有独立遗漏。
5. 4379行中大量是测试/测试夹具，约1848行位于测试模块。不能以总行数认定过度设计。实质可简化点是未使用的Tauri插件配置层、过宽的生命周期锁范围，以及部分恢复/调度状态组合；签名、root身份、兼容性与回退本身不能一概删除。

### U-01：guardian 丢弃更新子进程，已有事务锁不负责回收（中；受安装方式限定）

调用链：

- current/crates/switcher-core/src/guardian.rs 737–746：macOS生产循环每60秒启动 spawn_blocking(spawn_public_update_check)，JoinHandle未保存。
- 同文件1162–1170：必须owner匹配、Public，并且developer_team成功；SourceLocal在1170拒绝，Personal在1167–1168直接返回。

- current/apps/desktop/src-tauri/src/main.rs 65–87：更新子进程走专用CLI入口，完成后exit，不建立普通GUI窗口。
- current/apps/desktop/src-tauri/src/update_runtime.rs 129–134、257–263：拿v2/lifecycle.lock并持到完整run_locked结束。

全文审查本组及补充全仓定位未发现SIGCHLD/SA_NOCLDWAIT/waitpid/waitid/reaper处理。静态可确定的是生产代码没有持有或等待自己spawn的std Child；在通常子进程回收语义下存在退出子进程积累风险。未做真机ps/进程树观察，因此不声称已观察到僵尸数量或资源耗尽。

精确限定：本问题不触发于本次SourceLocal安装；触发于Public+DeveloperId且原生codesign通过。不存在“每60秒并发安装”的结论，因为子进程中的共享LifecycleLock排斥真实更新任务。codesign与启动前校验发生在该锁外，且spawn_blocking没有任务inflight限制，慢/挂起的预检查工作可重叠；这是不同于更新事务并发的风险。

最小修复：guardian保留一个后台任务句柄，只在上一次完成后调度；让后台任务持有Child并wait/try_wait回收，或在既有spawn_blocking内使用status等待。增加有限超时及取消后的回收，不让等待阻塞保镖主循环。不引入独立进程管理服务。删除范围仅限无所有者的spawn模式；保留Public调度、SourceLocal gate与安装事务锁。

验证建议：隔离的短命子进程确认被wait；模拟长前置校验证明最多一个更新worker；独立确认持锁时第二更新任务返回lifecycle_busy。已有1338–1374测试只覆盖第二次取锁失败与调度持久化，不能作Child回收证据。

## 条件性缺陷：当前pins=None，启用可信远程更新前必须处理

### U-04：同版本不是正常“无更新”结果，Public可能变成每分钟重复检查（中；高置信静态）

updates.rs 131–215的authenticate_candidate唯一成功类型是新Candidate；167–169把等版本（包括相同precedence）与降级合为downgrade_or_same_version。ReleaseTransport.check 1635–1656不支持UpToDate或204等正常无更新结果。runtime409–430只有获得更高版本Candidate后才schedule.success(Check)。

runtime329–333只对update_network或HTTP错误做transient_failure；同版本错误走authorization_cancelled，updates.rs960–962仅清in_flight，不更新next_check_at。因此到期的Public收到服务器当前已安装版本时，下一轮guardian60秒仍到期；每次重复网络、锁及错误消息，直到服务提供更高版本或手工暂停。clock Resume后的AwaitingVerifiedRefresh也只有获得新Candidate才可在runtime428执行record_verified_success，已是最新版不能借同源正常刷新恢复clock；同版广告刷新有可能另行恢复共享clock，但不能依赖广告提供更新功能恢复通道。

最小修复：把“验证合法元数据”与“判断需要安装”分开；合法、上下文正确、时间与反重放检查通过的等版本结果返回UpToDate，更新下次检查时间/最近成功验证时间而不下载或安装。保持真正降级/旧序列拒绝，并为不可重试的坏元数据设置明确重试时机，避免无期限分钟循环。不要删除版本防降级或让无签名的空响应重置可信状态。

验证建议：初次到期、服务器合法同版、12小时内再次被guardian触发时无第二次请求；same precedence build metadata不安装；合法同版可完成clock恢复；旧序列与错误签名保持拒绝。当前测试1163–1218只证实同版拒绝，没有正常“已是最新”控制流测试。

### U-05：恢复入口先要求待恢复的guardian健康，可能把中断更新锁在门外（中；高置信条件）

runtime385–400调用顺序为validate_installed → pinned_installation → NativeUpdateCoordinator::new → recover。install.rs456–462的validate_installed同时要求身份与validate_installed_health；465–471读取guardian-health。pinned_installation689把任何此类错误统一转为installed_identity_required。

若可信远程更新中断导致guardian失联/健康过期，身份仍可验证、旧兼容组件可恢复，仍可能在385–388提前拒绝，执行不到400的恢复。coordinator.recover（install1040–1136）恰是先恢复PKG/App，再1113 wait_installed核验旧组件。坏健康状态作为恢复前置条件形成闭环，而且错误文案把health问题说成identity缺失。此处也影响本意允许“修复journal存在时检查更新”的分支：runtime389–392在健康门槛之后，实际是否被拦需结合guardian健康的生成规则。

最小修复：为恢复入口提供已验证owner、edition、root记录和组件签名身份的接口，与健康门槛分开；先以足够身份边界恢复已记录事务，再做完整健康检查，正常新安装仍须健康/兼容就绪。不要为了可恢复而信任可写用户记录或允许任意路径。缺失helper/不可信身份是否能走专用恢复安装器，需按root边界单独设计，不应放宽为“任何坏安装都自动修复”。

验证建议：保留root身份但guardian heartbeat缺失/过期的中断journal，可到达受控恢复；伪造身份仍在恢复前拒绝。无实际中断安装/恢复验收，本组不声称当前真机中断过。

### U-06：检查/下载持账号生命周期锁，慢网络阻塞正常使用（中；条件性可用性）

runtime257–263一次拿共享LifecycleLock覆盖run_locked全流程，包括execute_pinned409–415元数据请求、453/493下载、583–609工件下载；ReleaseTransport1573–1579每请求配置10秒连接、120秒总超时。storage.rs12明确同一锁用于账号写入、launch、安装。远程服务慢/大工件下载时，用户启动或切换遇到lifecycle_busy，可持续多个请求的等待时间。账户事务与安装互斥合理，纯网络读取持此锁没有同等必要性。

最小修复：用更新任务自己的单飞锁/令牌保证检查下载不重复；短持生命周期锁读取/提交版本与状态，网络在锁外；安装及组件恢复仍持全程LifecycleLock，提交前重新核对candidate、sequence、安装身份及账号/修复空闲。不要简单去掉锁后造成过期状态覆盖。已有in_flight持久化每次load都会recover_process清空（runtime167–169），不能在释放全局锁后直接依赖它充当跨进程排斥。

验证建议：可控慢本地transport中，检查/下载不挡普通launch/账号查看；并发下载只有一个；真正安装阻止账号切换；下载完成前后发生新候选时不能提交旧状态。此为后续远程启用前的设计收敛，当前pins=None不会遇到长网络持锁。
